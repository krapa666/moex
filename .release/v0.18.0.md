# MOEX Fair Price v0.18.0

Minor release adding forward-only shadow consensus history and operational drift monitoring while keeping production consensus unchanged.

## Added

- Added persistent safe aggregate history in `shadow_consensus_snapshots`.
- Added periodic batch capture from `arsagera-worker`.
- Added public history API:
  - `GET /api/analytics/shadow-consensus/history?ticker=SBER&days=90`
- Added public drift API:
  - `GET /api/analytics/shadow-consensus/drift?ticker=SBER&days=30`
- Added local-only manual capture API:
  - `POST /api/analytics/shadow-consensus/capture`
- Added Analytics forward chart `production median vs shadow weighted`.
- Added operational drift status and reasons.

## Batch evaluation

Periodic capture does not call the expensive accuracy-history builder once per ticker.

The shadow engine now creates a shared calculation context for the current target year:

- analyst tables;
- selected `pre_year/mid_year/year_end` training snapshot;
- historical accuracy samples;
- no-lookahead eligible training set.

That context is built once per capture and reused for all tickers in the primary table.

The existing single-ticker `GET /api/analytics/shadow-consensus` contract is unchanged.

## Forward-only history

Only shadow results with at least two comparable current sources are persisted.

Each snapshot stores aggregate values only:

- ticker and target year;
- training snapshot and capture time;
- source/training coverage counts;
- min/max source weight without source identity;
- median/weighted net profit;
- median/weighted target price;
- weighted-vs-median delta;
- current price and median/weighted market gap.

The table does **not** store analyst names, source-level forecasts, or source-level weights.

History starts after deployment of v0.18.0. Existing forecast revisions are not backfilled because reconstructing old source sets and weights from current state would risk hindsight bias.

## Capture schedule

Defaults:

```dotenv
SHADOW_HISTORY_ENABLED=true
SHADOW_HISTORY_INTERVAL_HOURS=6
SHADOW_HISTORY_RUN_ON_STARTUP=true
SHADOW_HISTORY_RETENTION_DAYS=730
```

Startup capture runs after configured forecast and actual-result startup synchronizations. Expired rows are pruned during capture.

The recurring capture keeps the same configured interval but its phase is shifted by **15 minutes** relative to the worker start. With the default six-hour source-sync cadence this makes forecast-source jobs due first and the shadow snapshot due 15 minutes later, reducing the risk of recording a mixed state while some source jobs are still starting. The initial startup snapshot remains strictly after the startup sync sequence.

These variables are optional. Existing `.env` files continue to work unchanged.

## Drift monitoring

Drift compares only snapshots from the latest target year.

A status is not classified until both conditions hold:

- at least 3 snapshots;
- at least 24 hours of forward history.

Before that the status is `insufficient`.

Operational signals:

- current weighted-vs-median target divergence;
- step change in divergence from the previous snapshot;
- max-weight concentration relative to equal weighting;
- relative movement gap between weighted and median over the monitoring window;
- training-snapshot regime change.

Policy thresholds:

| Signal | WATCH | ALERT |
| --- | ---: | ---: |
| absolute baseline divergence | `>= 10%` | `>= 20%` |
| absolute divergence step | `>= 5 pp` | `>= 10 pp` |
| weight concentration ratio | `>= 1.5x` | `>= 1.75x` |
| absolute relative movement gap | `>= 5 pp` | `>= 10 pp` |

A training snapshot change adds a WATCH reason unless a stronger ALERT already applies.

These are transparent engineering thresholds, not a statistical significance claim and not an investment signal.

## Analytics UI

The new `Shadow history и drift` panel shows:

- status `STABLE / WATCH / ALERT / accumulation`;
- snapshot count and history span;
- latest and median absolute weighted-vs-median divergence;
- latest weight concentration ratio;
- relative movement gap;
- median and weighted target chart;
- recent snapshots;
- human-readable reasons for WATCH/ALERT.

The UI never displays source identity or source-level weights from this history.

## Production boundary

**v0.18.0 does not promote weighted consensus to production.**

Unchanged:

- production median target price;
- fair-value formulas;
- expected-return calculations;
- Watchlist ranking;
- volume-monitor logic;
- weighting defaults from v0.15.

Readiness and forward drift monitoring remain evidence layers for a future explicit review/release.

## Database and configuration

- Database migration required: **yes**.
- New schema head: `0021_shadow_consensus_snapshots`.
- Manual Alembic command required: **no** — the backend container runs `alembic upgrade head` before startup.
- Mandatory `.env` changes: **no**.
