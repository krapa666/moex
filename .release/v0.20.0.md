# MOEX Fair Price v0.20.0

Minor release adding stateful, deduplicated email notifications for significant forward shadow-drift transitions while keeping production consensus unchanged.

## Added

- Added persistent per-ticker shadow drift state in `shadow_drift_states`.
- Added append-only transition/delivery ledger in `shadow_drift_notification_events`.
- Added stateful transition processing after each shadow-history capture.
- Added one-digest-per-cycle SMTP delivery using the existing volume-monitor SMTP transport.
- Added retry handling for failed mail and `superseded` handling for stale events.
- Added public safe notification status/event APIs.
- Added local-only test-email endpoint.
- Added notification state and recent transition history to the Analytics global shadow overview.
- Added backend state-machine tests and Playwright coverage.
- Updated README, Analytics/shadow methodology and deployment documentation.

## State machine

The first observed state is bootstrap-only and never generates email.

Notifiable transitions:

```text
STABLE → WATCH     subject to per-ticker cooldown
STABLE → ALERT     immediate
WATCH  → ALERT     immediate escalation
WATCH  → STABLE    recovery if the incident was actually notified
ALERT  → STABLE    recovery if the incident was actually notified
```

Same-state observations do not create repeated events or mail.

`ALERT → WATCH` remains actionable and is recorded without a recovery email. Full recovery is `STABLE`.

Transitions to/from `insufficient` and target-year rollover are persisted but not mailed.

## Bootstrap and deployment safety

`SHADOW_NOTIFICATIONS_ENABLED=false` by default.

The state ledger is still maintained while notification delivery is disabled. This provides a current baseline without sending a deployment flood and prevents old suppressed transitions from being sent retroactively if notifications are enabled later.

## Cooldown

Default:

```dotenv
SHADOW_NOTIFICATION_COOLDOWN_HOURS=24
```

Cooldown protects repeated `STABLE → WATCH` re-entry caused by threshold flapping.

It does not suppress escalation to `ALERT` or a valid recovery notification.

## Durable delivery

Potential mail transitions enter `pending`.

SMTP failure changes the event to `failed`; it can be retried on a later monitoring cycle up to:

```dotenv
SHADOW_NOTIFICATION_MAX_ATTEMPTS=5
```

Before retry, the event target year and destination state are compared with current drift state. If the event is already stale it becomes:

```text
delivery_status = superseded
```

and is not emailed.

## SMTP configuration

The feature reuses the existing volume-monitor SMTP variables:

```dotenv
VOLUME_SMTP_ENABLED=true
VOLUME_SMTP_HOST=...
VOLUME_SMTP_PORT=587
VOLUME_SMTP_USERNAME=...
VOLUME_SMTP_PASSWORD=...
VOLUME_SMTP_FROM=...
VOLUME_SMTP_STARTTLS=true
VOLUME_SMTP_SSL=false
VOLUME_PUBLIC_BASE_URL=https://moex.junnylab.ru
```

Shadow-specific optional settings:

```dotenv
SHADOW_NOTIFICATIONS_ENABLED=false
SHADOW_NOTIFICATION_EMAIL=
SHADOW_NOTIFICATION_COOLDOWN_HOURS=24
SHADOW_NOTIFICATION_HISTORY_DAYS=30
SHADOW_NOTIFICATION_MAX_ATTEMPTS=5
```

If `SHADOW_NOTIFICATION_EMAIL` is empty, `VOLUME_NOTIFICATION_EMAIL` is used.

Existing deployments require no `.env` changes unless email delivery should actually be enabled.

## API

Public safe operational status:

```http
GET /api/analytics/shadow-consensus/notifications/status
```

Public safe event history:

```http
GET /api/analytics/shadow-consensus/notifications/events?limit=50
```

Local-only SMTP test:

```http
POST /api/analytics/shadow-consensus/notifications/test
```

Public responses do not expose recipient addresses, SMTP credentials, source identities, source-level forecasts or source-level weights.

## Database

Database migration required: **yes**.

New schema head:

```text
0022_shadow_drift_notifications
```

Manual Alembic command required: **no**. Backend startup runs `alembic upgrade head` before Uvicorn.

## Production boundary

**v0.20.0 does not promote weighted consensus to production.**

Unchanged:

- production median target price;
- fair-value formulas;
- expected-return calculations;
- Watchlist ranking;
- volume-monitor logic;
- weighting defaults;
- readiness policy;
- drift thresholds.

Notifications are an observability layer over the forward shadow model and are not investment signals.
