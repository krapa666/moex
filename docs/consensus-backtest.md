# Backtest консенсуса чистой прибыли

## Назначение

Начиная с v0.15.0 MOEX Fair Price сравнивает несколько способов агрегировать **исторические прогнозы годовой чистой прибыли** на одном и том же наборе наблюдений. С v0.16.0 поверх этого backtest добавлена отдельная robustness-проверка: результат раскладывается по годам и тикерам, проверяется leave-one-out и прогоняется по фиксированной сетке параметров weighting.

Backtest является исследовательским слоем. Он не меняет текущий production consensus target price, fair value, Watchlist или расчёт доходности.

## Что именно тестируется

Для каждой пары `ticker + fiscal_year` и выбранного snapshot берутся источники, у которых существует сохранённый прогноз ЧП этого года до фиксированной отсечки.

Наблюдение попадает в backtest только если:

1. существует канонический факт годовой ЧП;
2. на одной и той же отсечке доступны минимум два источника прогноза;
3. все методы оцениваются на этой же паре `ticker + fiscal_year`.

По умолчанию сравниваются:

- **Медиана** — production-style baseline для агрегирования;
- **Среднее** — обычное арифметическое среднее прогнозов;
- **Accuracy-weighted** — консервативное среднее с весами из более ранней подтверждённой истории.

Backtest работает по прогнозам **чистой прибыли**, а не по target price. Для годовой ЧП существует объективный опубликованный факт; у аналитической fair value нет единственного объективного «факта цены», с которым корректно обучать веса.

## Snapshot

Используются те же фиксированные отсечки, что и в source accuracy:

| Snapshot | Отсечка |
| --- | --- |
| `pre_year` | 1 января финансового года |
| `mid_year` | 1 июля |
| `year_end` | 1 января следующего года |

Для каждого источника используется последняя прогнозная ревизия строго раньше соответствующей отсечки.

## Защита от look-ahead bias

Вес источника для наблюдения года `Y` разрешено обучать только на accuracy samples, которые удовлетворяют одновременно двум условиям:

1. их `fiscal_year < Y`;
2. канонический факт для этого старого года имеет известный `reported_at`, и эта дата строго раньше целевой backtest-отсечки.

Если `reported_at` отсутствует, историческое наблюдение **не используется для обучения веса**. Оно может участвовать в обычной ретроспективной оценке своего собственного года, но не доказывает, что результат был известен в нужный момент прошлого времени.

Текущая таблица `actual_net_profits` хранит канонический факт, а не полную историю его рестейтментов. Поэтому при более позднем рестейтменте `reported_at` отражает текущую каноническую публикацию; backtest намеренно ведёт себя консервативно и может исключить такой sample из более раннего training window.

## Accuracy-weighted метод

Для каждого источника рассчитывается медианная sMAPE только по доступной на тот момент training history.

Сначала определяется общий prior:

```text
global_error = median(sMAPE всех доступных training samples)
```

Если training history вообще отсутствует, используется консервативный prior `50%`.

Для источника с `n` наблюдениями:

```text
reliability = n / (n + k)
```

где `k` — `shrinkage_samples`, по умолчанию `5`.

Затем:

```text
effective_error = reliability × source_median_error
                + (1 - reliability) × global_error
```

Это shrinkage к общему prior: источник с несколькими удачными попаданиями не получает экстремальный вес.

Далее ошибка ограничивается снизу:

```text
effective_error = max(effective_error, error_floor_percent)
```

по умолчанию `error_floor_percent = 5%`.

Относительный score:

```text
score = reference_error / effective_error
```

Score ограничивается диапазоном:

```text
1 / relative_score_cap <= score <= relative_score_cap
```

по умолчанию `relative_score_cap = 2`.

После этого scores нормализуются до суммы весов `1`.

Таким образом, даже очень сильная/слабая короткая история не может создать неограниченный вес. Новый источник без истории получает нейтральный prior.

Если доступной training history нет ни у одного источника, все scores одинаковы и `Accuracy-weighted` математически совпадает с обычным средним.

## Метрики методов

Каждый метод оценивается на **одинаковом наборе backtest observations**:

- median sMAPE;
- mean sMAPE;
- median absolute error, млрд ₽;
- mean absolute error, млрд ₽;
- mean bias `Forecast - Actual`;
- sign accuracy;
- число наблюдений, тикеров и финансовых лет.

Дополнительно возвращаются:

- `median_smape_delta_vs_median_pp`;
- `mean_smape_delta_vs_median_pp`.

Положительная delta означает, что метод имеет меньшую ошибку, чем baseline-медиана. Например `+3.2 п.п.` означает улучшение sMAPE на 3.2 процентного пункта.

## Robustness analysis

С v0.16.0 backtest дополнительно отвечает на вопрос: является ли преимущество weighted-метода устойчивым, а не следствием одного удачного сегмента или одного набора параметров.

### Срез по финансовым годам

Для каждого `fiscal_year` отдельно считаются baseline-медиана и accuracy-weighted метод на наблюдениях только этого года. Возвращаются median/mean sMAPE и delta weighted к медиане.

Если общий результат положительный, но один или несколько лет имеют отрицательную delta, это видно явно и не скрывается общим средним.

### Срез по тикерам

Та же процедура выполняется отдельно для каждого тикера. В интерфейсе слабые значения сортируются первыми, чтобы сразу видеть бумаги, на которых weighting ухудшает прогноз.

### Leave-one-out

Выполняются две серии evaluation jackknife:

- поочерёдно исключается один тикер;
- поочерёдно исключается один финансовый год.

После исключения заново считается качество weighted относительно медианы на **оставшемся evaluation-наборе**.

Это намеренно не переобучает training history. Цель проверки — понять, зависит ли итоговое преимущество от вклада одного тикера или года. Если после исключения конкретного сегмента delta меняет знак, общий результат чувствителен к этому сегменту.

### Чувствительность к параметрам

Используется фиксированная диагностическая сетка:

```text
shrinkage_samples = 2, 5, 10
error_floor_percent = 2.5, 5, 10
relative_score_cap = 1.5, 2, 3
```

Всего `3 × 3 × 3 = 27` комбинаций.

Для каждой комбинации используется тот же no-lookahead принцип и тот же набор eligible `ticker + fiscal_year`. Возвращаются weighted median/mean sMAPE и delta к медиане.

Robustness API дополнительно показывает:

- сколько тикерных срезов имеют положительную median-delta;
- сколько годовых срезов имеют положительную median-delta;
- в скольких leave-one-out случаях преимущество сохраняется;
- в скольких из 27 параметрических комбинаций weighted остаётся лучше медианы;
- минимальную и максимальную median-delta по сетке.

В коде нет произвольного бинарного флага `robust=true`. Решение о production weighting должно основываться на фактическом покрытии и стабильности, а не на скрытом пороге.

## API

Публичная безопасная сводка backtest:

```http
GET /api/analytics/consensus-backtest
```

Параметры:

- `snapshot=pre_year|mid_year|year_end`;
- `min_sources` — минимум источников, default `2`;
- `shrinkage_samples` — default `5`;
- `error_floor_percent` — default `5`;
- `relative_score_cap` — default `2`.

Сводка не содержит реальных имён аналитиков и безопасна для internet/read-only режима.

Robustness endpoint:

```http
GET /api/analytics/consensus-backtest/robustness
```

Параметры:

- `snapshot=pre_year|mid_year|year_end`;
- `min_sources` — default `2`.

Ответ содержит только публичные агрегаты, финансовые годы и MOEX-тикеры. Имена аналитиков, source weights и source-level forecasts в него не входят.

Подробный audit endpoint:

```http
GET /api/analytics/consensus-backtest/observations
```

Он возвращает прогнозы, веса и training sample counts по реальным `analyst_name`, поэтому требует explicit local scope.

Дополнительные фильтры: `ticker`, `fiscal_year`, `limit`.

## Интерфейс

В `/analytics/` рядом с source accuracy показывается таблица методов для выбранного snapshot:

- метод;
- число наблюдений, тикеров и лет;
- median/mean sMAPE;
- delta к медиане;
- MAE;
- bias;
- sign accuracy.

Ниже отображается robustness-блок:

- общий weighted delta;
- доля положительных срезов по тикерам и годам;
- сохранение преимущества при leave-one-out;
- число положительных случаев в сетке из 27 параметров;
- диапазон delta по этой сетке;
- таблицы по годам и тикерам;
- разворачиваемая таблица параметрической чувствительности.

Один selector snapshot управляет source accuracy, основным consensus backtest и robustness analysis, чтобы метрики всегда относились к одной временной отсечке.

## Когда можно включать weighted consensus в production

Сам факт, что weighted-метод лучше на текущей истории, недостаточен. Перед изменением боевого consensus нужны как минимум:

- достаточное число наблюдений и финансовых лет;
- устойчивое улучшение не только mean, но и median error;
- проверка по нескольким snapshot;
- отсутствие преимущества, создаваемого одной компанией или одним годом;
- разумная чувствительность к `k`, error floor и weight cap;
- повторная проверка после расширения factual coverage.

До отдельного решения production consensus остаётся прежним.
