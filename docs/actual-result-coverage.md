# Actual Results Coverage

`Actual Results Coverage` показывает, какая доля накопленной исторической прогнозной базы уже может быть честно проверена по канонической фактической годовой чистой прибыли.

Функция добавлена в v0.26.0 как диагностический слой поверх уже существующих `forecast_revisions` и `actual_net_profits`. Она не меняет production consensus и не является автоматическим promotion gate.

## Зачем это нужно

Метрики точности источников и backtest консенсуса полезны только там, где одновременно существуют:

1. прогноз, сохранённый до заранее определённой исторической отсечки;
2. канонический фактический результат по тому же тикеру и финансовому году.

Если фактических результатов мало, небольшая выборка может создавать ложное впечатление о качестве источника или метода. Coverage делает этот пробел видимым до принятия решений по weighted consensus или canary expansion.

## API

```text
GET /api/analytics/actual-net-profits/coverage
```

Параметры:

- `snapshot=pre_year|mid_year|year_end` — историческая отсечка прогноза;
- `years=1..10` — размер окна, по умолчанию 5 завершённых финансовых лет;
- `end_year=YYYY` — необязательный последний финансовый год;
- `missing_limit=0..200` — максимум детальных пропусков `ticker + year`, по умолчанию 50.

Если `end_year` не задан, используется предыдущий календарный год. Текущий и будущие финансовые годы отклоняются: отсутствие финального годового факта для незавершённого года не должно искусственно ухудшать coverage.

## Знаменатель

Одна прогнозная пара — это уникальная комбинация:

```text
source/table + analyst_name + ticker + fiscal_year
```

Пара попадает в знаменатель, только если в `forecast_revisions` есть конечное числовое значение прогноза ЧП, сохранённое **до** выбранной отсечки:

```text
pre_year  -> до 1 января fiscal_year
mid_year  -> до 1 июля fiscal_year
year_end  -> до 1 января fiscal_year + 1
```

Это сохраняет тот же no-hindsight принцип, который используется в Source Accuracy.

## Числитель

Пара считается покрытой, если в `actual_net_profits` существует канонический факт для:

```text
ticker + fiscal_year
```

Один факт может разблокировать оценку нескольких прогнозных источников, поэтому API отдельно показывает:

- `missing_forecast_pairs` — сколько source/ticker/year наблюдений пока нельзя оценить;
- `missing_actual_records` — сколько уникальных `ticker/year` фактов нужно добавить, чтобы закрыть эти наблюдения.

## Агрегации

Ответ содержит:

- общий `coverage_percent`;
- число прогнозных и покрытых пар;
- число уникальных тикеров;
- количество канонических фактов в выбранном окне;
- `by_year` — покрытие по финансовым годам;
- `by_source` — покрытие по прогнозным источникам;
- `missing_actuals` — приоритетный список отсутствующих `ticker/year`.

`missing_actuals` сортируется прежде всего по количеству источников, которые блокирует один отсутствующий факт. Это позволяет сначала заполнять факты с максимальным приростом полезной исторической выборки.

## UI

На `/analytics/` внутри блока точности источников показывается панель **Покрытие фактическими результатами**:

- общий процент покрытия;
- покрытые / все исторические прогнозные пары;
- количество уникальных недостающих фактов;
- количество фактов в каноническом реестре;
- таблицы по годам и источникам;
- список приоритетных `ticker/year` для заполнения.

Панель использует тот же `snapshot`, что и Source Accuracy, и пересчитывается после изменения среза. После обновления списка фактов она также перечитывает coverage.

Для интернет-доступа имена аналитиков маскируются тем же механизмом, что и в существующей Source Accuracy UI.

## Что coverage не означает

Высокий coverage не доказывает точность прогнозов и не является достаточным условием для включения weighted consensus.

Низкий coverage также не означает, что источник плохой: это характеристика полноты фактической базы относительно уже сохранённых прогнозов.

Поэтому v0.26.0 **не**:

- меняет production median;
- расширяет controlled canary;
- включает auto-promotion;
- меняет веса источников;
- меняет forecast parsers или cadence синхронизации.

Решения о дальнейшей активации weighted/canary должны опираться одновременно на достаточный coverage, размер forward-only выборки, устойчивость метрик и текущие safety gates.

## База данных и конфигурация

Новая таблица не создаётся. Используются существующие:

- `forecast_revisions`;
- `actual_net_profits`.

Миграция БД: **не требуется**.

Новые переменные окружения: **не требуются**.
